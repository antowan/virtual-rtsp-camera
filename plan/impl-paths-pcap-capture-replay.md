# Implementation Paths — PCAP Capture & Replay

> Branch: `feature/pcap-capture-replay`  
> Plan: `plan/feature-pcap-capture-replay-1.md`

This document proposes concrete implementation paths for the three technically uncertain areas from the plan's Phase 1 spike. Each path is described with enough detail to start coding immediately.

> **⚠️ Superseded in part by plan revision 1.1.** Three recommendations below did not survive review and were changed before implementation:
>
> | Section | Original recommendation | Outcome |
> |---|---|---|
> | Path A | `scapy` for PCAP I/O | **Kept**, with a lazy import so the CLI hot path does not pay for it. |
> | Path B | **B1** — raw UDP into MediaMTX | **Rejected.** The `source: rtp://` syntax does not exist (MediaMTX spells it `udp+rtp://` and needs `rtpSDP`), and more importantly MediaMTX re-packetises RTP, destroying the wire-level fidelity that is the whole point of replay. Replaced by a self-hosted minimal RTSP server (plan ALT-005). |
> | Path C | **C1** — asyncio byte-pipe camera → MediaMTX `ANNOUNCE` | **Rejected as written.** RTSP is not a symmetric byte pipe: the camera is a server and MediaMTX expects a client doing ANNOUNCE/SETUP/RECORD. A real proxy is server-downstream + client-upstream with URI/Transport rewriting, and MediaMTX is not in that path. **C2 (`tcpdump` side-car) is the current capture story**, and the whole proxy is deferred to plan revision 1.2. |
>
> The "Docker / Linux capability constraints" section at the end remains accurate and is the reason `tcpdump` is a viable capture path today.

## Path A — PCAP I/O library choice

### Option A1 — `scapy` (recommended for Phase 1)

`scapy` is a pure-Python library that can read/write `.pcap` and `.pcapng` files without a system `libpcap` at runtime. Already common in security tooling; well-maintained.

```python
# pyproject.toml addition
# dependencies = [..., "scapy>=2.5"]

from scapy.utils import PcapWriter, PcapReader
from scapy.layers.inet import UDP, IP
from scapy.layers.rtp import RTP

with PcapWriter("capture.pcap", append=False, sync=True) as w:
    w.write(pkt)  # any Scapy packet, timestamp preserved

for pkt in PcapReader("capture.pcap"):
    ts = float(pkt.time)
    raw = bytes(pkt[UDP].payload)  # raw RTP bytes
```

**Pros:** no C extension needed, works identically on macOS/aarch64, supports pcapng, good RTP dissector built-in.  
**Cons:** heavier install (~12 MB), starts slowly on first import (lazy build).

### Option A2 — `dpkt`

Tiny, pure-Python pcap **reader/writer** (`pip install dpkt`). Does not parse RTP natively — you'd do that yourself.

```python
import dpkt, time

with open("capture.pcap", "wb") as f:
    w = dpkt.pcap.Writer(f)
    w.writepkt(raw_ethernet_frame, ts=time.time())

with open("capture.pcap", "rb") as f:
    for ts, buf in dpkt.pcap.Reader(f):
        eth = dpkt.ethernet.Ethernet(buf)
        udp_payload = eth.data.data.data  # Ethernet→IP→UDP→payload
```

**Pros:** extremely lightweight, zero dependencies, fast import.  
**Cons:** no pcapng support (pcap only), manual RTP framing.

### Option A3 — `python-libpcap` (C binding, future optimisation)

Wraps `libpcap` directly for live capture. Needed if we want to capture from a real NIC in proxy mode without `tcpdump`. Optional extra in `pyproject.toml`.

```toml
[project.optional-dependencies]
pcap = ["python-libpcap>=0.5"]
```

**Recommendation:** start with **A1 (scapy)** for both file write and replay. Add A3 as an optional extra later if live NIC capture proves necessary.

## Path B — RTP injection / replay approach

This is the most consequential decision. Three viable approaches:

### Option B1 — Raw UDP socket sender (recommended)

Read RTP packets from PCAP, send them as raw UDP datagrams directly to the MediaMTX RTP input port. MediaMTX accepts external RTP publishers via its `sourceType: rtp` path configuration.

```
PCAP → Python RtpSender → UDP → MediaMTX (rtp://127.0.0.1:8004/cam1) → RTSP readers
```

MediaMTX path config snippet (generated by `mediamtx.py`):

```yaml
paths:
  cam1:
    source: rtp://127.0.0.1:8004
    sourceOnDemand: no
```

Python sender core:

```python
import socket, time


class RtpSender:
    def __init__(self, host: str, port: int):
        self._sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        self._addr = (host, port)

    def send_at(self, pkt: bytes, wall_time: float) -> None:
        # Coarse sleep then busy-wait for the final 2 ms
        remaining = wall_time - time.perf_counter()
        if remaining > 0.002:
            time.sleep(remaining - 0.002)
        while time.perf_counter() < wall_time:
            pass
        self._sock.sendto(pkt, self._addr)
```

**Pros:** zero re-encoding, preserves original RTP sequence numbers and timestamps, simplest integration point, no ffmpeg dependency for replay.  
**Cons:** requires MediaMTX `sourceType: rtp` support (verified in MediaMTX ≥ 1.5); SDP must be pushed separately via RTSP ANNOUNCE or MediaMTX API.

### Option B2 — ffmpeg `-f rtp_mpegts` re-publish

Extract raw video from PCAP, pipe into `ffmpeg -i pipe: -f rtsp rtsp://127.0.0.1:8554/cam1`. Easier to wire up but **re-encodes**, breaking the exact packet timing goal.

**Rejected** for the core replay use-case. Keep as a fallback for PCAPs where SDP cannot be reconstructed.

### Option B3 — TCP-interleaved RTSP push to MediaMTX

Open a TCP connection to MediaMTX, perform a proper RTSP ANNOUNCE/SETUP/RECORD exchange, then inject `$`-framed RTP packets. Fully standard but requires implementing an RTSP client state machine in Python.

```python
# Rough sketch
sock.sendall(b"ANNOUNCE rtsp://127.0.0.1:8554/cam1 RTSP/1.0\r\n...")
# → 200 OK
sock.sendall(b"SETUP rtsp://127.0.0.1:8554/cam1/trackID=0 RTSP/1.0\r\n...")
# → 200 OK, Session: …
sock.sendall(b"RECORD rtsp://127.0.0.1:8554/cam1 RTSP/1.0\r\n...")
# → 200 OK
# Now inject: b"$\x00" + len(rtp_pkt).to_bytes(2,"big") + rtp_pkt
```

**Pros:** works everywhere, SDP declared upfront, no extra MediaMTX config.  
**Cons:** 80–100 lines of RTSP state machine to get right; TCP framing adds latency overhead.

**Recommendation:** implement **B1 (raw UDP)** first — fewest moving parts, fastest to build and test. Add **B3** as a fallback for environments where UDP is blocked between containers.

## Path C — Proxy mode architecture

### Option C1 — Python asyncio TCP relay (recommended)

Write a pure-Python `asyncio` RTSP reverse-proxy. Intercepts the RTSP negotiation and forks each `$`-framed RTP packet to both the downstream MediaMTX ANNOUNCE socket and the `PcapWriter`.

```
Real camera ─TCP─► RtspProxy (Python asyncio) ─TCP─► MediaMTX ANNOUNCE
                          │
                          └──► PcapWriter  (writes .pcapng)
```

Key structure in `proxy.py`:

```python
import asyncio


class RtspProxy:
    async def run(self, upstream_url: str, local_path: str, pcap_writer: PcapWriter):
        reader_up, writer_up = await asyncio.open_connection(upstream_host, upstream_port)
        reader_dn, writer_dn = await asyncio.open_connection("127.0.0.1", mediamtx_port)

        async def forward(src, dst, *, tee: bool = False):
            while True:
                chunk = await src.read(65536)
                if not chunk:
                    break
                dst.write(chunk)
                if tee:
                    pcap_writer.write_packet(chunk, time.time())

        await asyncio.gather(
            forward(reader_up, writer_dn, tee=True),  # upstream → local (capture)
            forward(reader_dn, writer_up),  # local → upstream (RTSP replies)
        )
```

**Pros:** pure Python, no OS tools needed, works inside Docker, captures everything including the RTSP handshake, exact bytes preserved.  
**Cons:** RTSP TCP interleaving requires correct `$`-frame boundary detection to isolate individual RTP packets for the PCAP; a naive chunked read doesn't guarantee packet boundaries.

### Option C2 — `tcpdump` side-car (simplest for Phase 1 spike)

Spawn `tcpdump -i eth0 -w capture.pcap host <camera_ip>` alongside the existing ffmpeg publisher. No proxy needed — MediaMTX itself connects to the camera in pull mode, and `tcpdump` records at the NIC level.

```
MediaMTX (source: rtsp://camera) ← tcpdump records everything on eth0
```

**Pros:** zero new Python network code, captures at kernel level (no missed packets), pcap is valid immediately.  
**Cons:** captures all traffic to that IP (noisy), can't be easily filtered per-stream, doesn't work when camera and station are on the same Docker bridge subnet loopback.

**Recommendation:** use **C2 (tcpdump side-car)** for the Phase 1 feasibility spike (TASK-004) to validate the replay approach end-to-end quickly. Then implement **C1 (asyncio relay)** for the production proxy mode (Phase 3).

## Docker / Linux capability constraints

These findings apply directly to the `vcam` Docker image and `docker-compose.yml`.

### What the default image already has

`python:3.12-slim` ships with `CapEff: 0xa80425fb` for the **root** user, which includes `cap_net_raw`. This means:

- **`AF_PACKET` raw sockets work out of the box** — no extra `cap_add` needed in `docker-compose.yml`.
- `tcpdump` (once installed with `apt-get install tcpdump`) can capture immediately **when the process runs as root**.

### The non-root problem

The `vcam` Dockerfile runs as `USER vcam` (uid 1000). When a process drops to a non-root UID, Linux clears all effective capabilities unless they are inherited via **ambient caps** or baked into the **file capabilities** of the binary.

Observed in a Linux container test environment:

| Scenario | Works? |
|---|---|
| Root container, `tcpdump` | ✅ |
| uid 1000, no file caps | ❌ `Operation not permitted` |
| uid 1000 + `setcap cap_net_raw+eip /usr/bin/tcpdump` (at build time) | ✅ `2.0K pcap written` |
| uid 1000 + `--cap-add=NET_RAW` in compose | ❌ Ambient caps not inherited without explicit `capsh --ambient` wrapper |

### Confirmed solution: file capabilities on `tcpdump` binary

Set `cap_net_raw` as a file capability on `tcpdump` at image build time. The binary then elevates only `cap_net_raw` for its own process, regardless of the calling UID. This is the standard way tcpdump is shipped on many Linux distros.

```dockerfile
# In the runtime stage of Dockerfile:
RUN apt-get install -y --no-install-recommends tcpdump libcap2-bin \
    && setcap cap_net_raw+eip /usr/bin/tcpdump \
    && rm -rf /var/lib/apt/lists/*
```

No changes to `docker-compose.yml` needed — **no `cap_add` required**.

### What about promiscuous mode (`-p` / `AF_PACKET` with `IFF_PROMISC`)?

The `any` pseudo-interface (`tcpdump -i any`) **cannot** be put into promiscuous mode on Linux — this is a kernel limitation, not a Docker restriction:

```
tcpdump: WARNING: any: That device doesn't support promiscuous mode
```

This does **not matter for our use-case**: we are capturing traffic to/from the vcam container's own `eth0` (the Docker bridge veth). Promiscuous mode would only be needed to capture traffic destined for _other_ hosts on the same segment. Capturing on `eth0` with no `-p` flag works perfectly and produced valid PCAPs in tests.

### Network mode considerations

| Network mode | Capture target | Notes |
|---|---|---|
| `bridge` (default) | `eth0` inside container | ✅ Works. Sees only the container's own traffic. |
| `host` | Any host NIC | ✅ Works. Sees all host traffic. Good for capturing camera traffic when camera is on the LAN. |
| Custom bridge | `eth0` inside container | ✅ Observed in a Linux container test environment. |
| Container-to-container (same bridge) | `eth0` | ✅ Captures traffic from MediaMTX and ffmpeg processes in the same network namespace. |

### Seccomp profile

The test environment used Docker's built-in `seccomp` profile (`name=seccomp,profile=builtin`). All syscalls required by `tcpdump` and raw socket operations (`socket(AF_PACKET)`, `recvfrom`, `bind`) are allowed by the default profile — no custom seccomp override needed.

### Summary table

| Requirement | Mechanism | docker-compose.yml change? |
|---|---|---|
| `tcpdump` available | `apt-get install tcpdump` in Dockerfile | No |
| Non-root capture | `setcap cap_net_raw+eip /usr/bin/tcpdump` in Dockerfile | No |
| `libpcap` for Python | `apt-get install libpcap-dev` in Dockerfile | No |
| Capture host NIC traffic | `network_mode: host` | Yes (optional, only if camera is on LAN) |
| Promiscuous mode | Not needed | — |
